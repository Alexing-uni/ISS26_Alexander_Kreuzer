Progetto it.unibo.virtualRobot2026 – DDR formalizzato e ambiente WebGL

Introduction

VirtualRobot26 – Definizione formale del DDR
Goal: Fornire un Differential Drive Robot (DDR) virtuale con una definizione formale del comportamento di basso livello, esposto via HTTP e WebSocket, e visualizzato in tempo reale in una scena WebGL (three.js) che simula l'ambiente fisico WEnv.

Il VirtualRobot26 e' lo strato di base su cui si appoggiano i progetti vrUsage26 (settimana 13) e tutti gli sviluppi successivi del corso sulla robotica. La sua peculiarita' e' di essere indistinguibile, dal punto di vista del client, da un robot fisico: stessi messaggi, stessi vincoli temporali, stessa interfaccia.

Requirements

R1  Fornire un robot DDR virtuale che risponda ai comandi standard:
        moveForward, moveBackward, turnLeft, turnRight, halt

R2  Esporre il robot via due protocolli equivalenti:
        - HTTP (request-response per comandi una tantum)
        - WebSocket (full-duplex per controllo continuo + observability)

R3  Visualizzare il robot e il suo ambiente in una scena WebGL nel
    browser (WEnv = Web Environment), in modo che lo studente veda
    in tempo reale gli effetti dei propri comandi.

R4  Supportare l'iniezione di scenari (obstacles, perimetri, oggetti
    interagibili) tramite file di configurazione caricabili a runtime.

R5  Fornire client di esempio in molteplici tecnologie (Android, web,
    Java) per documentare l'uso del protocollo.

Requirement analysis

Un robot virtuale e' un'utility didattica preziosa: consente di sviluppare e collaudare la logica applicativa senza dover gestire hardware fisico, batterie, attriti reali. Tuttavia, perche' sia utile, deve rispettare alcuni vincoli:

  • Determinismo "ragionevole": il robot virtuale non deve essere istantaneo. Un moveForward deve impiegare tempo realistico, in modo che il client debba gestire il problema di sincronizzazione.
  • Observability: deve emettere eventi (cambio posizione, collisione, fine movimento) che il client puo' osservare. Senza observability il client deve fare polling.
  • Trasporto neutrale: HTTP e WebSocket espongono le stesse primitive. Lo studente puo' scegliere il protocollo in base al proprio caso d'uso.
  • Ambiente caricabile: gli scenari (mappa, ostacoli) sono file JSON. Cambiare scenario non richiede ricompilare nulla.

Problem analysis

L'architettura del VirtualRobot26 si articola in tre livelli: 

   +---------------------------------+
   |  Browser (WEnv)                  |
   |   - three.js: scena 3D           |
   |   - WebSocket client             |
   |   - JS state machine             |
   +-------------------+--------------+
                       |
                       | WebSocket (ws://localhost:8090)
                       |
   +-------------------+--------------+
   |  Java Backend (Javalin)          |
   |   - HTTP /robot/* endpoints      |
   |   - WS message handler           |
   |   - Robot state machine          |
   +-------------------+--------------+
                       |
                       | observers
                       v
                +-----------------+
                | Subscribers     |
                | (vrUsage26 apps)|
                +-----------------+

Il problema piu' delicato e' la coerenza dello stato fra browser e backend. La scena WebGL deve riflettere fedelmente lo stato logico del robot, ma e' fisicamente separata dal motore di calcolo del movimento. La soluzione adottata e':

  1. il backend e' la fonte unica di verita': lo stato del robot vive solo li';
  2. la scena 3D e' una vista derivata: aggiorna mesh e position in base agli eventi WS in arrivo;
  3. i comandi del browser sono richieste al backend, non modifiche dirette dello stato.

Test plans

Il piano di collaudo prevede tre macro-fasi:

  1. Smoke test della scena WebGL: aprire node/WEnv/WebGLScene/indexOk.html in un browser locale. Deve apparire la scena 3D con il robot in posizione HOME.
  2. Test movimento manuale: nella pagina indexOkWithNaiveGui.html ci sono bottoni Forward/Back/Left/Right. Premerli e verificare il movimento.
  3. Test client programmatico: dalla cartella ClientExamples/AndroidClient (o equivalente Java) inviare i comandi via TCP/WS e verificare la coerenza scena/log.

Project

Il progetto e' un modulo Gradle con doppia natura: Java backend + asset web (HTML/JS/Three.js).

Backend Java

  • build.gradle, settings.gradle — build Java/Kotlin
  • Sorgenti del server VirtualRobot26 (servlet HTTP + WebSocket + motore movimento)

Ambiente WebGL (WEnv)

  • node/WEnv/WebGLScene/ — scena 3D del robot:
    • indexOk.html — scena base funzionante
    • indexOkWithNaiveGui.html — scena con bottoni di controllo
    • indexNoControl.html — solo visualizzazione
    • indexOccupied.html — scena con ostacoli
    • models/spaceship.json — mesh 3D alternativa
  • node/WEnv/README.md — istruzioni di setup

Client di esempio

  • node/WEnv/ClientExamples/AndroidClient/ — client Android (Kotlin) che si connette al VirtualRobot via TCP. Mostra:
    • TCPClient.kt, TCPEndPoint.kt — astrazione del trasporto
    • OutputChannel.kt, ConnectionListener.kt — pattern observer
    • MainActivity.kt — UI di test

Testing

Il testing del VirtualRobot26 e' principalmente integrazione: il backend Java + la scena WebGL + un client devono coordinarsi coerentemente. La strategia adottata e':

  • Unit test sulla state machine del robot (puramente Java, senza GUI ne' rete).
  • Integration test con un client headless che invia una sequenza di comandi e verifica gli eventi emessi.
  • System test manuale con la scena WebGL aperta per verificare l'animazione e la corretta resa visiva di ogni comando.

Maintenance

Il VirtualRobot26 e' deliberatamente generico: non assume nulla sull'applicazione che lo usa. Le evoluzioni naturali sono:

  • Sensori virtuali: aggiungere camera virtuale, sonar virtuale, accelerometro virtuale. La scena WebGL puo' calcolare i dati e inviarli come stream sui WS.
  • Multi-robot: estendere il backend per supportare N robot contemporanei, ciascuno con la propria sessione WS. La scena WebGL li renderizza nello stesso ambiente.
  • Twin digitale: collegare il VirtualRobot26 a un robot fisico in modo che le due entita' (virtuale + fisica) siano in sync. Caso d'uso classico di Digital Twin.

Il valore didattico del progetto risiede nella separazione netta fra "intenzione" (cosa vuole fare l'applicazione: percorrere il perimetro) e "esecuzione" (come il robot si muove fisicamente). Il VirtualRobot26 e' il banco di prova ideale per studiare questa separazione prima di passare al robot fisico (Picow + sonar HC-SR04).
