Laboratorio 2 – Analisi Critica Comparativa

Autore: Alexander Kreuzer  |  Corso ISS26 – DISI, Università di Bologna  |  22 aprile 2025

1. Introduzione

In questo laboratorio si analizzano e confrontano due approcci per descrivere e configurare un sistema software che offre un servizio di calcolo matematico (funzione eval):

  1. Approccio imperativo con Javalin: SistemaSJavalin e SistemaSJavalinBetter
  2. Modello dichiarativo ad attori QAK: sistema descritto con il DSL QAK (QActors come FSM)
Domanda centrale: Cosa guadagna e cosa perde lo sviluppatore passando da un sistema orientato agli oggetti con thread a un sistema ad attori con messaggi tipati?

2. Approccio 1: SistemaSJavalin / SistemaSJavalinBetter

Descrizione generale

SistemaSJavalin è una classe Java/Kotlin che configura un server Javalin in modo imperativo: nel metodo doJob() (o configureTheSystem() nella versione "Better") si registrano route HTTP e handler WebSocket direttamente come lambda.

SistemaSJavalinBetter fattorizza il codice in metodi separati (setWorkHTTP(), setWorkWS()), migliorando la separazione delle responsabilità ma mantenendo lo stesso paradigma imperativo.

Frammento rappresentativo

// SistemaSJavalinBetter – configurazione WS
app.ws("/eval", ws -> {
    ws.onConnect(ctx -> { ctx.send("{\"msg\":\"welcome\"}"); });
    ws.onMessage(ctx -> {
        String m      = ctx.message();
        double x      = readInputWS(m);
        double result = eval(x);       // blocca il thread se x > 4.0
        ctx.send("risultato WS=" + result);
    });
    ws.onClose(ctx -> { System.out.println("connection closed"); });
});

Caratteristiche principali

  • Configurazione imperativa: il sistema viene definito passo dopo passo nel codice. La topologia è incorporata nel flusso di esecuzione, non descritta separatamente.
  • Modello di concorrenza basato su thread: Javalin gestisce un pool di thread internamente. Ogni connessione WebSocket occupa un thread; se eval impiega troppo tempo, il thread rimane bloccato.
  • Stato condiviso: il campo app è uno stato mutabile condiviso. Aggiungere logica concorrente richiede sincronizzazione esplicita.
  • Messaggi non tipati: i messaggi sono scambiati come stringhe o JSON grezzi, senza contratto formale sul formato o sul protocollo.
  • Accoppiamento trasporto–logica: l'handler WS chiama direttamente eval(), accoppiando il trasporto con la logica di dominio.
  • Distribuzione limitata: il sistema risiede in una sola JVM; scalarlo richiede infrastruttura esterna.

Vantaggi

  • + Codice familiare per sviluppatori Java.
  • + Configurazione diretta e semplice per servizi piccoli.
  • + Poche dipendenze; facile da avviare e debuggare.
  • + Libreria Javalin ben documentata con molti esempi.

Svantaggi

  • – Difficile ragionare sulla concorrenza man mano che il sistema cresce.
  • – Operazioni bloccanti negli handler penalizzano la scalabilità.
  • – Topologia e logica di business accoppiati: cambiare porta o protocollo richiede modifiche al codice.
  • – Nessun supporto nativo per distribuzione o messaggistica MQTT.
  • – I messaggi sono stringhe senza contratto formale; gli errori di formato emergono a runtime.

3. Approccio 2: Modello ad Attori QAK

Descrizione generale

QAK (QActors) è un DSL esterno (costruito su Xtext) per descrivere sistemi distribuiti basati su attori. Ogni QActor è una Macchina a Stati di Moore (FSM): ha stati con azioni, transizioni tipate e una coda di messaggi privata. Il sistema viene descritto in modo dichiarativo: quali attori esistono, in quale contesto (nodo = JVM + IP:porta) risiedono e come si scambiano messaggi.

Frammento rappresentativo

System sistemaSQak

Request   evalReq  : evalReq(X)
Reply     evalResp : evalResp(RESULT) for evalReq

Context ctxSistemaSQak ip [host="localhost" port=8050]

QActor evaluator context ctxSistemaSQak {
    State s0 initial { }
    Transition t0 whenRequest evalReq -> doEval

    State doEval {
        onMsg(evalReq : evalReq(X)) {
            [# val x      = payloadArg(0).toDouble()
               val result = Math.sin(x) + Math.cos(Math.sqrt(3.0)*x)
               val R      = result.toString() #]
            replyTo evalReq with evalResp : evalResp($R)
        }
    }
    Goto s0
}

Caratteristiche principali

  • Configurazione dichiarativa: la topologia (contesti, attori, messaggi) è descritta nel DSL. Il codice generato (Kotlin) separa il "cosa" dal "come".
  • Messaggi tipati: Dispatch, Request/Reply ed Event sono tipi di messaggi di prima classe. Il compilatore valida gli identificatori.
  • FSM esplicita: il comportamento di ogni attore è una FSM leggibile; stati e transizioni sono visibili nel DSL.
  • Concorrenza senza stato condiviso: ogni QActor è una coroutine Kotlin con la propria coda di messaggi. La comunicazione avviene sempre per messaggio.
  • Trasporto intercambiabile: lo stesso modello QAK funziona su TCP o MQTT senza modificare il codice dell'attore.
  • Distribuzione naturale: spostare un QActor su un altro nodo richiede solo di cambiare host nel suo contesto.
  • Scalabilità estrema: essendo coroutine Kotlin, è possibile istanziare migliaia di QActors in una sola JVM.

Vantaggi

  • + Chiara separazione tra topologia, messaggi e logica di business.
  • + La FSM rende il comportamento esplicito e verificabile.
  • + Messaggi tipati: errori rilevati in fase di compilazione/progettazione.
  • + Nessuno stato condiviso: la concorrenza è sicura per design.
  • + Distribuzione e cambio di protocollo senza toccare la logica dell'attore.
  • + Migliaia di attori leggeri grazie alle coroutine Kotlin.
  • + Supporto MQTT nativo: pronto per IoT e microservizi.

Svantaggi

  • – Curva di apprendimento maggiore: bisogna padroneggiare DSL, modello FSM e frammenti Prolog.
  • – L'ecosistema QAK è più piccolo rispetto ai framework Java convenzionali.
  • – Debug più complesso: l'esecuzione asincrona di coroutine richiede strumenti specifici.
  • – Overhead per sistemi molto semplici dove un POJO con Javalin sarebbe sufficiente.

5. Riflessione critica

La differenza fondamentale tra i due approcci non è solo tecnica ma filosofica: SistemaSJavalin descrive come costruire il sistema (imperativo), mentre il modello QAK descrive cosa è il sistema (dichiarativo).

L'approccio Javalin è adatto quando la velocità di sviluppo è prioritaria e il sistema è piccolo e monolitico. Man mano che il sistema cresce, l'assenza di tipizzazione nei messaggi, l'accoppiamento tra trasporto e logica e la difficoltà di ragionare sulla concorrenza diventano debito tecnico crescente.

Il modello QAK obbliga il progettista a pensare in termini di attori, messaggi e stati prima di scrivere una sola riga di codice di business. Questa disciplina, sebbene costosa all'inizio, produce sistemi più robusti, più facili da scalare e da distribuire.

Nel contesto del corso ISS26, il sistema delle lucciole (Task 2–4) è un buon esempio di perché il modello ad attori scala meglio: 100 lucciole come 100 thread del SO sarebbero costose e soggette a problemi di sincronizzazione; 100 QActors come coroutine Kotlin sono leggere, autonome e si coordinano tramite eventi senza alcuno stato condiviso.

6. Conclusione

Per sistemi distribuiti, reattivi e di media/alta complessità, il modello ad attori QAK offre vantaggi strutturali chiari rispetto all'approccio SistemaSJavalin. La separazione dichiarativa dell'architettura, i messaggi tipati e il modello senza stato condiviso riducono gli errori concorrenti e facilitano l'evoluzione del sistema.

SistemaSJavalin / Better rimane valido come adattatore di ingresso (inbound adapter) all'interno di un sistema QAK: Javalin riceve la richiesta HTTP/WS e la trasforma in un messaggio QAK elaborato dall'attore corrispondente.
