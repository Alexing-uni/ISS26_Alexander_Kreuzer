Laboratorio 2 – Análisis Crítico Comparativo

Autor: Alexander Kreuzer | Curso ISS26 | 22 de abril de 2025

1. Introducción

En este laboratorio se analiza y compara dos enfoques para describir y configurar un sistema software que ofrece un servicio de cálculo matemático (función eval):

  1. Enfoque imperativo con Javalin: SistemaSJavalin y SistemaSJavalinBetter
  2. Modelo declarativo de actores QAK: sistema descrito con el DSL QAK (QActors como FSMs)

La pregunta central es: ¿Qué gana y qué pierde el desarrollador al pasar de un sistema orientado a objetos con hilos a un sistema de actores con mensajes tipados?

2. Enfoque 1: SistemaSJavalin / SistemaSJavalinBetter

Descripción general

SistemaSJavalin es una clase Java/Kotlin que configura un servidor Javalin de forma imperativa: en el método doJob() (o configureTheSystem() en la versión "Better") se registran rutas HTTP y manejadores WebSocket directamente como lambdas.

SistemaSJavalinBetter refactoriza el código en métodos separados (setWorkHTTP(), setWorkWS()), mejorando la separación de responsabilidades pero manteniendo el mismo paradigma imperativo.

Fragmento representativo

// SistemaSJavalinBetter – configuración WS
app.ws("/eval", ws -> {
    ws.onConnect(ctx -> { ctx.send("{\"msg\":\"welcome\"}"); });
    ws.onMessage(ctx -> {
        String m      = ctx.message();
        double x      = readInputWS(m);
        double result = eval(x);       // bloquea el hilo si x > 4.0
        ctx.send("risultato WS=" + result);
    });
    ws.onClose(ctx -> { System.out.println("connection closed"); });
});

Características clave

  • Configuración imperativa: el sistema se define paso a paso en código Java/Kotlin. No hay descripción abstracta de la arquitectura; la topología está embebida en el flujo de ejecución.
  • Modelo de concurrencia basado en hilos: Javalin gestiona un pool de hilos internamente. Cada conexión WebSocket ocupa un hilo; si eval tarda mucho (CommUtils.delay(8000)), ese hilo queda bloqueado.
  • Estado compartido: el campo app (de tipo Javalin) es estado mutable compartido. Añadir lógica concurrente más compleja requiere sincronización explícita.
  • Mensajes sin tipado: los mensajes se intercambian como cadenas de texto o JSON crudos. No hay contrato formal sobre el formato del mensaje ni sobre el protocolo de comunicación.
  • Adaptador de entrada = lógica de negocio: el manejador WS llama directamente a eval(), acoplando el transporte (WebSocket) con la lógica de dominio.
  • Distribución limitada: el sistema vive en una sola JVM. Escalarlo a múltiples nodos requiere añadir infraestructura externa (balanceador, broker de mensajes, etc.).

Ventajas

  • + Código familiar para desarrolladores Java.
  • + Configuración directa y sencilla para servicios pequeños.
  • + Pocas dependencias; fácil de arrancar y depurar.
  • + Biblioteca Javalin bien documentada con ejemplos abundantes.

Desventajas

  • – Difícil de razonar sobre concurrencia a medida que el sistema crece.
  • – Operaciones bloqueantes en handlers penalizan la escalabilidad.
  • – Topología y lógica de negocio acopladas: cambiar el puerto o el protocolo requiere modificar el código.
  • – No hay soporte nativo para distribución o mensajería MQTT.
  • – Los mensajes son cadenas sin contrato formal; los errores de formato se detectan en tiempo de ejecución.

3. Enfoque 2: Modelo de Actores QAK

Descripción general

QAK (QActors) es un DSL externo (construido sobre Xtext) para describir sistemas distribuidos basados en actores. Cada QActor es una Máquina de Estados de Moore (FSM): tiene estados con acciones, transiciones tipadas y una cola de mensajes privada. El sistema se describe de forma declarativa: qué actores existen, en qué contexto (nodo = JVM + IP:puerto) viven y cómo intercambian mensajes.

Fragmento representativo (equivalente al sistema SistemaSJavalin en QAK)

System sistemaSQak

Request   evalReq  : evalReq(X)
Reply     evalResp : evalResp(RESULT) for evalReq

Context ctxSistemaSQak ip [host="localhost" port=8050]

QActor evaluator context ctxSistemaSQak {
    State s0 initial { }
    Transition t0 whenRequest evalReq -> doEval

    State doEval {
        onMsg(evalReq : evalReq(X)) {
            [# val x      = payloadArg(0).toDouble()
               val result = Math.sin(x) + Math.cos(Math.sqrt(3.0)*x)
               val R      = result.toString() #]
            replyTo evalReq with evalResp : evalResp($R)
        }
    }
    Goto s0
}

Características clave

  • Configuración declarativa: la topología (contextos, actores, mensajes) se describe en el DSL. El código generado (Kotlin) separa el "qué" del "cómo".
  • Mensajes tipados: Dispatch, Request/Reply y Event son tipos de mensajes de primera clase. El compilador valida los identificadores y los payloads Prolog se unifican automáticamente (onMsg).
  • FSM explícita: el comportamiento de cada actor es una FSM legible. Los estados y las transiciones son visibles en el DSL, facilitando la comprensión y la revisión del diseño.
  • Modelo de concurrencia sin estado compartido: cada QActor es una corrutina Kotlin con su propia cola de mensajes. No hay acceso compartido entre actores; la comunicación es siempre por mensaje.
  • Transporte intercambiable: el mismo modelo QAK funciona sobre TCP o MQTT sin cambiar el código del actor. La directiva mqttBroker activa el transporte MQTT.
  • Distribución natural: mover un QActor a otro nodo es tan simple como cambiar host en su contexto. La infraestructura de routing es automática.
  • Escalabilidad extrema: al ser corrutinas Kotlin (no hilos del SO), es posible instanciar miles de QActors en una sola JVM. Véase la demo de 100 luciérnagas (Task 4).

Ventajas

  • + Separación clara entre topología, mensajes y lógica de negocio.
  • + La FSM hace el comportamiento explícito y auditable.
  • + Mensajes tipados: errores detectados en tiempo de compilación/diseño.
  • + Sin estado compartido: la concurrencia es segura por diseño.
  • + Distribución y cambio de protocolo sin tocar la lógica del actor.
  • + Miles de actores ligeros gracias a corrutinas Kotlin.
  • + Soporte MQTT nativo: listo para IoT y microservicios.

Desventajas

  • – Curva de aprendizaje mayor: hay que dominar el DSL, el modelo FSM y los fragmentos Prolog.
  • – El ecosistema QAK es más pequeño que el de frameworks Java convencionales.
  • – Depuración más compleja: la ejecución asíncrona de corrutinas requiere herramientas específicas.
  • – Sobrecoste para sistemas muy simples donde un POJO con Javalin sería suficiente.

5. Reflexión crítica

La diferencia fundamental entre los dos enfoques no es solo técnica sino filosófica: SistemaSJavalin describe cómo construir el sistema (imperativo), mientras que el modelo QAK describe qué es el sistema (declarativo).

El enfoque Javalin es adecuado cuando la velocidad de desarrollo es prioritaria y el sistema es pequeño y monolítico. Conforme el sistema crece, la ausencia de tipado en los mensajes, el acoplamiento entre transporte y lógica, y la dificultad para razonar sobre la concurrencia se convierten en deuda técnica creciente.

El modelo QAK obliga al diseñador a pensar en términos de actores, mensajes y estados antes de escribir una sola línea de código de negocio. Esta disciplina, aunque costosa al inicio, produce sistemas más robustos, más fáciles de escalar y de distribuir. El hecho de que el mismo modelo funcione sobre TCP, MQTT o Ethereum sin cambiar el actor ilustra la potencia de la abstracción.

En el contexto de la asignatura ISS26, el sistema de luciérnagas (Tasks 2–4) es un buen ejemplo de por qué el modelo de actores escala mejor: 100 luciérnagas como 100 hilos del SO serían costosas y propensas a problemas de sincronización; 100 QActors como corrutinas Kotlin son ligeras, autónomas y se coordinan mediante eventos sin ningún estado compartido.

6. Conclusión

Para sistemas distribuidos, reactivos y de mediana/alta complejidad, el modelo de actores QAK ofrece ventajas estructurales claras sobre el enfoque SistemaSJavalin. La separación declarativa de la arquitectura, los mensajes tipados y el modelo sin estado compartido reducen los errores concurrentes y facilitan la evolución del sistema.

SistemaSJavalin / Better sigue siendo válido como adaptador de entrada (inbound adapter) dentro de un sistema QAK, tal como se muestra en la integración Javalin–QAK del laboratorio: Javalin recibe la petición HTTP/WS y la transforma en un mensaje QAK que es procesado por el actor correspondiente.
