Progetto vrUsage26 – Esempi d'uso del VirtualRobot26

Introduction

RobotObj26 come oggetto osservabile
Goal: Sviluppare un'applicazione che comanda il Differential Drive Robot (DDR) per farlo percorrere il perimetro di una stanza rettangolare vuota, partendo da una posizione HOME e fermandosi al ritorno. Il progetto rappresenta il riferimento operativo delle lezioni del 12/05 e 13/05.

L'esercitazione introduce due percorsi progettuali:
  • uso diretto del VirtualRobot26 tramite WebSocket (paradigma technology-dependent);
  • uso indiretto tramite POJO RobotObj26 che incapsula il trasporto e si comporta come oggetto osservabile (paradigma technology-agnostic).

Il confronto fra i due approcci e' tema centrale della lezione: il primo esibisce tutti i dettagli del protocollo, il secondo li nasconde dietro un oggetto Java tradizionale.

Requirements

R1  Costruire un sistema software che comanda un DDR per fargli percorrere
    il perimetro di una stanza rettangolare vuota, partendo da HOME e
    fermandosi al ritorno in HOME.

R2  Il DDR e' sensibile anche ai dati di Radar:
    - se il Radar rileva un 'intruso' a distanza < DMIN:
        - se il DDR e' in movimento, si ferma fino a quando il Radar non
          rileva piu' alcuna minaccia
        - se il DDR e' fermo in HOME, ruota fino alla scomparsa
          della minaccia

R3  Calcolare la lunghezza del lato della stanza in unita' robot,
    tarando lo step temporale appropriato per la combinazione
    velocita'/dimensione fisica della stanza simulata.

R4  Costruire una mappa della stanza in cui il robot opera, assumendo
    ostacoli fissi e perimetro libero da ostacoli entro la banda di
    larghezza pari al robot.

Requirement analysis

L'analisi parte da una distinzione cruciale: il DDR fisico non e' deterministico nei tempi di esecuzione di un comando di movimento. Una moveForward mantenuta per n millisecondi non produce esattamente n*v unita' di spostamento perche':

  • l'avvio richiede un transitorio (accelerazione);
  • la frenata richiede un tempo di decelerazione;
  • l'ambiente (attrito, inerzia, batteria) introduce variabilita'.

Da cio' deriva la necessita' di tre primitive ortogonali:

  • moveForward / turnLeft / turnRight / halt — comandi base.
  • step(t) — comando di alto livello: muoviti per t ms e fermati. La calibrazione di t e' specifica del robot.
  • Observable pattern — il robot deve poter notificare quando un comando termina, in modo che l'applicazione si sincronizzi senza polling.

Problem analysis

Le due architetture proposte nel progetto materializzano due punti del continuum vicino al protocollo ↔ vicino al dominio:

Aspetto Uso diretto WebSocket Uso via RobotObj26 (POJO)
Esempio BoundaryWalkNaiveUsingWs26.java BoundaryWithBasicMoves.java, BoundaryWithStep.java
API esposta JSON su WS (ctx.send("{cmd:'forward'}")) Metodi Java (robot.forward(), robot.step(t))
Concorrenza Callback @OnMessage Observer pattern + Thread interno
Calibrazione Hard-coded nel codice Centralizzata in RobotObj26.create(...)
Riusabilita' Bassa (un'app, un protocollo) Alta (il POJO incapsula il trasporto)

L'analisi del problema porta a preferire la versione POJO per i casi d'uso applicativi: il BoundaryWithStep e' molto piu' leggibile di BoundaryWalkNaiveUsingWs26 perche' parla il linguaggio del dominio (step, turn, halt) anziche' quello del trasporto (JSON message, session). 

// BoundaryWithStep - chiaro, dominio-orientato
RobotObj26 robot = RobotObj26.create(addr, null, logFName);
for (int side = 0; side < 4; side++) {
    for (int i = 0; i < sideLength; i++) robot.step(stepTime);
    robot.turnLeft();
}
robot.halt();

Test plans

Il piano di collaudo procede in quattro fasi:

  1. Calibrazione step: eseguire calibrate/TuneSteptime.java e regolare il parametro stepTime fino a ottenere un movimento di una unita' grid per step.
  2. Misura della stanza: eseguire calibrate/RoomSideLength.java per calcolare la lunghezza del lato in unita' robot.
  3. Test di movimento naive: eseguire BoundaryWalkNaiveUsingWs26. Analizzare il log e i thread (uso di CommUtils.aboutThreads).
  4. Test di movimento ad alto livello: eseguire BoundaryWithStep e verificare che il robot percorra il perimetro completo in tempo prevedibile.

Project

Il progetto e' un modulo Gradle indipendente con la seguente organizzazione:

Sorgenti

  • src/it/unibo/virtualRobot2026/clients/ — Client diretti su protocollo:
    • TestMovesUsingHttp.java, TestMovesUsingWs26.java — primi test di movimento
    • BoundaryWalkNaiveUsingHttp.java, BoundaryWalkNaiveUsingWs26.java — perimeter walk grezzo via HTTP/WS
  • src/appls/ — Applicazioni ad alto livello che usano RobotObj26:
    • BoundaryWithBasicMoves.java — perimeter walk con comandi base
    • BoundaryWithStep.java — perimeter walk con step (lettura immediata)
  • src/calibrate/ — Utility di calibrazione:
    • TuneSteptime.java — taratura del parametro stepTime
    • RoomSideLength.java — misura del lato della stanza
  • utils/NaiveGui.html — pagina HTML per visualizzare il movimento del robot
  • utils/map/RobotDir.java — utility per direzione/orientamento

Risorse

  • src/main/resources/logback.xml — configurazione log
  • libs/ — dipendenza RobotObj26.jar

Testing

Il testing e' interattivo e basato su analisi log + thread inspection:

  • Le applicazioni emettono log dettagliati su logs/vrusage26.log. La configurazione e' duplicata in src/logback.xml per supportare l'esecuzione tramite "Run As → Java Application" da Eclipse.
  • Ogni applicazione invoca CommUtils.aboutThreads("name") per stampare lo stato dei thread attivi al momento. Il confronto fra log produced da diverse versioni evidenzia il diverso modello di concorrenza (callback vs observer).
  • Per i test che richiedono il VirtualRobot26 attivo, occorre avviare prima il server WebGLScene/indexOk.html del progetto it.unibo.virtualRobot2026, che e' la scena WebGL con il robot animato.
