Progetto sistemasqak – SistemaS modellato in QAK

Introduction

SistemaS – DAI MONOLITI AI MICROSERVIZI
Goal: Riformulare nel linguaggio QAK il servizio di valutazione matematica già implementato in Java/Javalin (SistemaSJavalinBetterApplMsgs), dimostrando come lo stesso comportamento possa essere descritto in modo dichiarativo come una Macchina a Stati Finiti con messaggi tipati.

Il progetto realizza la Fase 3 dell'evoluzione di SistemaS:
  • Fase 1 – Monolite Javalin in Java (AService/Sprint1/SistemaSJavalin).
  • Fase 2 – Refactoring ad attori con Protoactor (SistemaSProtoactor).
  • Fase 3 – Modello dichiarativo in QAK (questo progetto).

Requirements

R1  Realizzare un servizio che valuti il valore di una funzione matematica
    a partire da un input numerico ricevuto da un client esterno.

R2  Il servizio deve supportare due paradigmi di interazione:
       - Dispatch (fire-and-forget): il client invia il valore senza
         attendere risposta.
       - Request / Reply: il client attende il risultato della
         valutazione.

R3  Il modello QAK deve essere funzionalmente equivalente al
    SistemaSJavalinBetter: stesso input, stesso output, stesso protocollo
    semantico.

R4  Mantenere disaccoppiate la logica di valutazione (funzione matematica)
    dalla logica di trasporto (messaggi QAK), in linea con i principi
    Clean Architecture.

Requirement analysis

Il problema della valutazione di una funzione matematica può essere riletto come:

  • un attore servente che attende richieste, calcola il risultato e (eventualmente) risponde;
  • un attore cliente che invia richieste e riceve la risposta.

Le due modalità di interazione si traducono in due primitive QAK distinte:

  • Dispatch eval : arg(V) – messaggio puntuale senza attesa di risposta. L'attore che lo riceve esegue il calcolo e termina la transazione. Equivalente a una POST HTTP fire-and-forget.
  • Request evalr : argr(V) con Reply evalreply : value(V) for evalr – richiesta sincrona tipata. Il chiamante è bloccato fino alla ricezione della risposta. Equivalente a una GET HTTP con response.

Questo doppio canale è una caratteristica nativa di QAK: lo stesso attore può esporre contemporaneamente entrambe le semantiche senza modificare il proprio codebase di base.


Problem analysis

Il problema progettuale principale è la corretta definizione delle transizioni di stato dell'attore sistemas. La FSM deve poter:

  1. essere in idle in attesa di un messaggio (sia Dispatch che Request);
  2. ricevere un messaggio e passare a uno stato di gestione specifico (handleEval o handleRequest);
  3. elaborare il payload, calcolare il risultato e (nel caso di Request) rispondere;
  4. tornare nello stato di attesa.

Una peculiarità del DSL QAK è che la dichiarazione delle transizioni può essere ripetuta dopo ogni stato, evitando il costrutto "loop globale". Ciò rende l'FSM molto leggibile ma richiede attenzione: dimenticare la riga Transition t0 ... dopo uno stato significa che l'attore termina dopo la prima richiesta. 

Transition t0
    whenMsg eval      -> handleEval
    whenRequest evalr -> handleRequest

State handleEval {
    onMsg( eval : arg(X) ) {
        [# val V = payloadArg(0).toDouble() #]
        [# val R = eval(V) #]
        println("$name | result=$R") color magenta
    }
}
Transition t0
    whenMsg eval      -> handleEval
    whenRequest evalr -> handleRequest

Un secondo problema riguarda l'esposizione esterna del servizio. Mentre SistemaSJavalin espone direttamente endpoint HTTP/WS, il QActor sistemas riceve messaggi QAK. Per integrare un client HTTP "ingenuo" si introduce un inbound adapter Java (CallerSistemas.java in utils/sistemasqak/) che traduce richieste HTTP in messaggi QAK.


Test plans

Il piano di collaudo prevede tre livelli di verifica:

  1. Test funzionale base: avviare sistemasqak e callermock. Verificare nel log che callermock emetta forward di Dispatch e request di Request, e che sistemas entri rispettivamente in handleEval e handleRequest.
  2. Test del payload: il valore V = 2.0 deve produrre R = 6.0 (la funzione di esempio è 3·x). La risposta deve arrivare a callermock con onMsg(evalreply : value(X)).
  3. Test del client esterno: con il CallerSistemas.java di utils/, verificare che il servizio risponda correttamente anche da un client HTTP esterno (compatibilità con il protocollo Javalin originale).

Project

Il progetto è un modulo Gradle indipendente. La struttura ricalca quella del progetto firefly (stesso scheletro Gradle/Eclipse).

  • sistemasqak/src/sistemas.qak – Modello QAK principale (versione del docente). Funzione di esempio: R = 3·x.
  • sistemasqak/src/demoApril21.qak – Variante personale che implementa la funzione complessa sin(x) + cos(√3·x), allineata a SistemaSJavalinBetterApplMsgs.
  • sistemasqak/src/it/unibo/sistemas/Sistemas.kt – Codice Kotlin generato dal plugin QAK per l'attore sistemas.
  • sistemasqak/src/it/unibo/callermock/Callermock.kt – Codice Kotlin per l'attore client di test callermock.
  • sistemasqak/src/it/unibo/ctxsistemas/MainCtxsistemas.kt – Entry point del sistema, carica sistemasqak.pl e sysRules.pl.
  • sistemasqak/sistemasqak.pl – Definizione Prolog del sistema (contesto, attori, messaggi).
  • sistemasqak/utils/sistemasqak/CallerSistemas.java – Client Java standalone per test di integrazione.

Testing

Il testing è condotto in due modalità:

  • Esecuzione diretta in Eclipse con il plugin QActork: avvio del contesto ctxsistemas, ispezione del log colorato. È il modo più rapido per validare un nuovo modello.
  • Esecuzione tramite Gradle: gradlew run avvia MainCtxsistemas. Per cambiare la classe Main da eseguire si modifica mainClassName in build.gradle.

Il client esterno CallerSistemas.java permette di invocare il servizio da una JVM separata, rendendo il test più realistico e confrontabile con la versione Javalin.


Maintenance

Il modello sistemasqak è progettato per essere il nucleo riusabile di servizi più complessi. Aggiungere una nuova operazione (es. derive, integrate) richiede tre modifiche locali:

  1. Aggiungere un Dispatch o Request nel preambolo del file .qak.
  2. Aggiungere uno stato handleNuovo con il calcolo specifico nel blocco [# ... #].
  3. Aggiornare la riga Transition t0 per includere il nuovo trigger.

Il build.gradle non richiede modifiche: il plugin QAK ricompila automaticamente. Questo dimostra l'estensibilità del modello rispetto a un equivalente Javalin (dove ogni nuovo endpoint richiede una app.post(...) esplicita più la deserializzazione manuale del payload).
