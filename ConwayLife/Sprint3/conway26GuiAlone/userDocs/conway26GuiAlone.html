conway26GuiAlone – ConwayLife con GUI HTML standalone

Introduction

GAME OF LIFE DI CONWAY
Goal: Realizzare una variante dello Sprint 3 di ConwayLife in cui la GUI HTML e' completamente standalone rispetto al core di dominio: il browser comunica via WebSocket o MQTT direttamente con il LifeController, senza intermediazione di un attore qak.

Questa versione del progetto consolida i pattern di interazione HTML+Javalin gia' presentati in conway26GuiHtml e li riorganizza in modo da rendere visibile la separazione fra:
  • il core di business ConwayLife (riusato come libreria conway26Java-1.0.jar del Sprint 1);
  • l'adapter di I/O (IoJavalin con varianti per porte e protocolli);
  • il controller applicativo (LifeControllerAdhoc che orchestra ConwayLife e GUI);
  • la pagina HTML che funge da view interattiva.

Requirements

R1  Realizzare una GUI HTML che soddisfi i requisiti di interazione del
    Sprint 3 di ConwayLife (start, stop, clear, edit celle, visualizzazione)
    senza dipendere da un attore qak intermedio.

R2  Riusare il core ConwayLife dello Sprint 1 come libreria binaria
    (conway26Java-1.0.jar), dimostrando che le interfacce IGrid/ICell/Life
    progettate al Sprint 1 supportano un'evoluzione tecnologica completa
    senza alcuna modifica al dominio.

R3  Esporre due varianti di trasporto:
        - WebSocket diretto via Javalin
        - MQTT per integrazione con sistemi distribuiti

R4  Mantenere la possibilita' di deployment in Docker (Dockerfile fornito).

Requirement analysis

Il progetto conway26GuiAlone si distingue da conway26GuiHtml e da conway26Protoactors per il modello di concorrenza:

Variante Concorrenza I/O Use case
conway26GuiHtml Threads Java + Javalin pool HTTP + WS Baseline web
conway26Protoactors Protoactors (attori in-process) HTTP + WS Refactoring ad attori
conway26GuiAlone Threads + Observer pattern WS + MQTT GUI distribuita / multi-client

L'analisi dei requisiti porta a strutturare l'applicazione in tre "interaction modules":

  • LifeGameInteraction — gestione della logica di gioco (start/stop/clear);
  • OutInGuiInteraction — gestione dell'invio stato verso la GUI;
  • CallerServerInteraction / ObserverServerInteraction — adattatori per client esterni.

Problem analysis

Il problema progettuale principale e' garantire che multiple GUI clienti possano connettersi simultaneamente al LifeController e vedere la stessa evoluzione del gioco. La soluzione adottata e' il pattern Observer esteso ai client WS: 

                            +-----------+
                  +-------> | Client 1  |
                  |         +-----------+
   LifeController +-------> | Client 2  |
   (Observable)   |         +-----------+
                  +-------> | Client N  |
                            +-----------+
        Ogni notifica e' inviata in fan-out su tutte le sessioni WS attive

Un secondo problema riguarda il controllo di flusso: se il LifeController emette generazioni a velocita' superiore a quanto la GUI puo' renderizzare, occorre evitare di saturare la rete. La soluzione e' un thread separato di calcolo con un piccolo delay per sincronizzare al framerate del browser.


Test plans

  1. Test del core riusato: verificare che la libs/conway26Java-1.0.jar sia caricata correttamente all'avvio.
  2. Test della GUI single-client: avviare MainConwayGui.java, aprire http://localhost:8080/page/LifeIInOutCanvas.html nel browser, premere Start e verificare l'animazione.
  3. Test multi-client: aprire la stessa URL in due browser; verificare che entrambi vedano in tempo reale la stessa evoluzione.
  4. Test MQTT: avviare un broker e variante IoJavalinMqtt; verificare che eventi cellstate arrivino al topic configurato.
  5. Test Docker: docker build -t conway26GuiAlone . e docker run -p 8080:8080 conway26GuiAlone.

Project

Il progetto e' un modulo Gradle con la seguente organizzazione:

Sorgenti

  • src/main/java/conway/io/:
    • IoJavalin.java — adapter Javalin di base (porta 8080)
    • IoJavalinFor8070.java — variante su porta 8070
    • IoJavalinMqtt.java — variante MQTT
  • src/main/java/conway26appl/:
    • LifeControllerAdhoc.java — controller orientato al riuso
    • LifeGameInteraction.java — modulo di interazione di gioco
    • OutInGuiInteraction.java — modulo I/O verso GUI
  • src/main/java/conway26appl/caller/:
    • CallerServerInteraction.java — client di test
    • ObserverServerInteraction.java — client osservatore
  • src/main/java/conwaygui/MainConwayGui.java — entry point dell'applicazione

Risorse web

  • src/main/resources/page/LifeIInOutCanvas.html — pagina principale con canvas
  • iomap.js, wscanvascontrol.js, outArea.js — script JS della GUI
  • mapstyle.css — stile della griglia

Dipendenze

  • libs/conway26Java-1.0.jar — core ConwayLife dello Sprint 1 (riuso senza modifiche)

Deployment

  • Dockerfile — image per deployment containerizzato
  • conway26GuiAlone.yaml — manifest Kubernetes/Docker Compose

Testing

Il testing e' principalmente manuale (System Test) data la natura interattiva del progetto. Il piano si articola in tre dimensioni:

  • Funzionale: verificare che ogni bottone (Start/Stop/Clear) abbia l'effetto atteso sul motore Conway;
  • Concorrenziale: aprire piu' tab del browser e verificare il fan-out;
  • Deployment: verificare l'avvio in container e l'esposizione corretta delle porte.

Maintenance

Il progetto e' progettato per essere il punto di riferimento per future evoluzioni della famiglia Conway:

  • GUI nativa: sostituire la pagina HTML con un'app Android/Desktop che parli lo stesso protocollo WS.
  • Persistenza: aggiungere un layer di storage (MongoDB, Redis) per salvare e ricaricare configurazioni iniziali.
  • Multi-game: estendere il backend per supportare multiple istanze parallele del gioco, ciascuna con il proprio ID di sessione.

Il riuso senza modifiche di conway26Java-1.0.jar e' la dimostrazione concreta del valore della progettazione orientata alle interfacce: il dominio Conway sviluppato 12 settimane fa ancora funziona, e funziona dentro un ambiente tecnologico completamente nuovo (Javalin, WebSocket, MQTT, Docker, multi-client).
