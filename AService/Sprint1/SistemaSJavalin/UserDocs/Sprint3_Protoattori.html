2. Analisi del Problema (Il limite del Monolite)

Nella prima fase del progetto (TODO 1), il sistema è stato concepito come un monolite. Il server web (Javalin) riceveva una richiesta HTTP e richiamava direttamente la funzione di business eval(x).

Il problema critico di questa architettura si manifesta quando x > 4.0. In questo caso, la funzione esegue un CommUtils.delay(8000) per simulare un calcolo oneroso. Essendo un sistema monolitico e sincrono, l'intero server web rimaneva bloccato per 8 secondi, incapace di gestire altre richieste in entrata (causando attese infinite o errori ERR_CONNECTION_REFUSED nel browser).

3. Architettura Logica e Refactoring (TODO 2)

Per risolvere il blocco del server, abbiamo effettuato una transizione verso un'architettura distribuita basata sul Paradigma ad Attori, utilizzando l'infrastruttura protoactor26 fornita dal corso.

  • MathActor: Un componente software (estende AbstractProtoactor26) che vive all'interno di un proprio ProtoActorContext26. Il suo unico scopo è ricevere messaggi di richiesta, eseguire il calcolo pesante nel proprio thread, e restituire un messaggio di risposta (Reply).
  • SistemaSProtoactor (Javalin): Il server web è stato snellito. Ora funge solo da "ponte" asincrono. Riceve la richiesta HTTP, costruisce un IApplMessage e lo invia all'attore. Utilizzando una CompletableFuture, Javalin libera immediatamente il thread web, delegando il lavoro e attendendo la risposta in modo non bloccante.

4. Implementazione (Snippets di rilievo)

La gestione asincrona lato Javalin per non bloccare il server:

app.get("/eval", webCtx -> {
    String parametro = webCtx.queryParam("x");
    IApplMessage req = CommUtils.buildRequest("javalinWeb", "doEval", parametro, "mathActor");
    
    // Delega asincrona all'attore
    CompletableFuture<String> promesa = CompletableFuture.supplyAsync(() -> {
        IApplMessage reply = mathActor.elabRequest(req);
        return "Risultato dall'attore: " + reply.msgContent();
    });
    
    // Chiusura non bloccante
    webCtx.future(() -> promesa.thenAccept(res -> webCtx.result(res)));
});

5. Testing e Deployment

Testing

Il sistema è stato testato con successo tramite browser:

  • http://localhost:8080/eval?x=2.0 → Risposta immediata (nessun ritardo).
  • http://localhost:8080/eval?x=5.0 → L'attore esegue il delay di 8 secondi, ma la console conferma l'invio della richiesta senza blocco del thread web.

Deployment (Docker)

Il sistema è stato "dockerizzato" con successo creando l'immagine sistema-protoactor tramite il comando Gradle distTar e un Dockerfile dedicato.
