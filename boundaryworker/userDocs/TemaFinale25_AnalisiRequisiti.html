TemaFinale25 – Analisi dei Requisiti

Requirements

Una compagnia di trasporto marittimo (company) intende automatizzare il carico di prodotti nella stiva (hold) di una nave, impiegando un Differential Drive Robot (cargorobot).

I prodotti vanno posti in container di dimensioni predefinite e registrati — specificando il peso — in un database tramite un servizio dedicato (productservice), che restituisce un identificatore univoco PID (numero naturale, PID > 0).

La stiva e' un'area rettangolare piatta con una porta di input/output (IOPort) e 4 slot per i container; l'area slot5 e' permanentemente occupata, gli altri slot sono inizialmente vuoti. Di fronte all'IOPort un sonar rileva la presenza di un container quando misura una distanza D < DFREE/2 per un tempo ragionevole (es. 3 secondi).

La compagnia chiede di costruire un sistema software (cargoservice) che:

  1. riceva la richiesta di caricare nella stiva un container con prodotto gia' registrato nel productservice. La richiesta e' rifiutata se:
    • il peso del prodotto e' troppo alto rispetto al carico massimo della nave MaxLoad > 0 kg;
    • la stiva e' gia' piena (4 slot occupati).
    Se accettata, il cargoservice associa uno slot al PID e ne restituisce il nome; attende quindi che il container venga consegnato all'IOPort. Nel frattempo, le altre richieste non vengono elaborate.
  2. rilevi (tramite il sonar) la presenza del container all'IOPort;
  3. garantisca che il container sia depositato dal cargorobot nello slot riservato. Al termine il cargorobot torna a HOME e il cargoservice puo' elaborare un'altra richiesta;
  4. mostri lo stato corrente della stiva in una web-gui aggiornata dinamicamente;
  5. interrompa ogni attivita' e accenda un LED se il sonar misura D > DFREE per almeno 3 secondi (sospetto guasto sonar). Le attivita' riprendono non appena D ≤ DFREE.

Analisi dei requisiti

Goal: formalizzare le entita' del dominio escludendo le ambiguita' del linguaggio naturale ed esprimendole in un linguaggio comprensibile a un computer (dichiarazioni Java per il dominio + modello qak per le interazioni).

Entita' formalizzate

Product — oggetto registrato nel productservice, identificato da PID e peso:

public class Product {
    int    pid;     // > 0, assegnato da productservice
    double weight;  // kg
}

ProductService — servizio esterno che fa da database dei prodotti:

public interface IProductService {
    int     register( double weight );  // restituisce PID univoco
    Product lookup( int pid );          // restituisce Product o null
}

Slot — area di stoccaggio nominata della stiva:

public class Slot {
    String  name;          // "slot1" .. "slot4", "slot5"
    int     posX, posY;    // posizione nella mappa (celle DR x DR)
    boolean occupied;
    Integer occupantPid;   // null se libero
    boolean permanent;     // true solo per slot5
}

Hold — aggregato dei 4 slot caricabili + slot5 permanente, con vincolo MaxLoad:

public class Hold {
    Slot[]  slots;         // 5 elementi: 4 caricabili + slot5 permanente
    double  maxLoad;       // kg, costante
    double  currentLoad;   // somma dei pesi dei container presenti
    String  reserve( Product p );    // restituisce slotName o null se non possibile
    void    confirmPlaced( String slotName, int pid );
    void    free( String slotName );
}

CargoRobot — DDR a basso livello (gia' disponibile come VirtualRobot26). Le mosse base e i comandi di pianificazione sono gia' formalizzati in robotservice26 e robotsmart26:

//gia' nei progetti esistenti
Request moverobot : moverobot(TARGETX, TARGETY, STEPTIME)   //robotsmart26
Request step      : step(TIME)                              //robotservice26
Dispatch move     : move(M)  "M = l|r|a|d|h"                //robotservice26

Sonar (IOPort) — sensore stazionario di fronte all'IOPort, realizzato dal PicoW (o dal mock mockPicowRadar.py), che pubblica via MQTT:

topic  : mqttdemotopic
payload: msg(sonardata, event, picow, none, sonardata(D), 0)
   D : distanza in cm (intero positivo)

IOPortDetector — filtra il flusso sonar e riconosce "container presente":

condizione  : D < DFREE/2 per almeno 3 secondi consecutivi
evento out  : containerAtIOPort()

Watchdog sonar — rileva il sospetto guasto:

condizione  : D > DFREE per almeno 3 secondi consecutivi
azione      : ledOn() + sospensione di tutte le attivita' cargoservice
ripristino  : D ≤ DFREE -> ledOff() + ripresa

WebGui — vista a 4 slot etichettati con PID e peso, piu' indicatore LED.

Struttura: sistema distribuito su 5 nodi

  • nodo PicoW (sonar IOPort + LED actuator) — o il mock Python;
  • nodo productservice (DB esterno dei prodotti);
  • nodo cargoservice (FSM principale + IOPortDetector + watchdog);
  • nodo robotsmart26 (capa di pianificazione + esecuzione comandi al robot);
  • nodo VirtualRobot26 (DDR virtuale, Docker).

Trattandosi di componenti logicamente (micro)servizi a scambio di messaggi, formalizziamo la struttura con il linguaggio qak.


Un modello dei requisiti

Il cargoservice e' il componente centrale: proattivo (gestisce sessioni di carico e coordina cargorobot) e reattivo (ai dati sonar dell'IOPort e al sospetto guasto). Lo modelliamo come QActor accompagnato da due QActor di supporto: iosensor (filtro container) e sonarwatch (watchdog guasti).

Domande aperte al committente

D1. Posizione di slot5: il quinto slot e' una posizione (X,Y) fissa e nota a priori,
    oppure il cargoservice la scopre interrogando la mappa all'avvio?

D2. Vincolo MaxLoad: "product-weight evaluated too high" significa
    (a) currentLoad + weight > MaxLoad (vincolo cumulativo) oppure
    (b) weight > MaxLoad (vincolo per-container)?

D3. Hold pieno: se i 4 slot sono occupati, la loadRequest e' rifiutata
    definitivamente o accodata fino a quando uno slot si libera (operazione
    di scarico non prevista nella spec)?

D4. Dimensione dei container: "predefined dimensions" significa che ogni
    container occupa esattamente 1 cella della mappa (1xDR x 1xDR), oppure
    puo' occupare piu' celle? Se piu' celle, qual e' la forma?

D5. Posizione dell'IOPort: e' una cella fissa nota o e' un parametro
    della mappa (es. caricato dal file tf25map.txt)?

D6. Comportamento in "suspended" (LED on): durante il sospetto guasto sonar,
    una loadRequest in arrivo va rifiutata con REASON=suspended, accodata,
    oppure il canale di richiesta e' chiuso?

D7. Persistenza dello stato hold: dopo riavvio del cargoservice, lo stato
    della stiva si recupera da DB / file, oppure si parte sempre da
    "hold vuoto + slot5 occupato"?

D8. Pickup automatico vs manuale: il cargorobot preleva fisicamente il container
    dall'IOPort (richiede attuatore di presa, non presente in VirtualRobot26)
    oppure simuliamo il pickup come "il robot e' arrivato al IOPort, viene
    caricato dall'operatore, poi parte verso lo slot"?

D9. Concorrenza delle richieste: la spec dice "in the meantime, other requests
    are not elaborated". Sono rifiutate (REASON=busy) o accodate FIFO?

Problematiche aperte (per l'analista)

P1 — Pickup/place: estensione del contratto robot o composizione nel cargoservice?
Aggiungere i nuovi messaggi pickup(PID) e place(SLOT) dentro robotsmart26 renderebbe esplicito il contratto, ma costringe a modificare un progetto del docente. In alternativa, il cargoservice puo' realizzare pickup/place componendo i messaggi gia' esistenti (moverobot verso IOPort / slot + delay simulati). Soluzione preferita: composizione nel cargoservice (non invasiva), con eventuale estensione di robotsmart26 in una seconda iterazione.
P2 — iosensor e sonarwatch: stesso QActor o separati?
Entrambi sottoscrivono lo stesso topic MQTT del sonar e applicano un filtro temporale. Tenerli separati semplifica la logica (ogni attore ha una sola condizione da riconoscere) e permette di testarli in isolamento. Costo: due connessioni al broker invece di una.
P3 — Granularita' del Test Plan automatizzato (richiesto dalla valutazione).
Il caso minimo significativo per la demo e': una loadRequest end-to-end che attraversa ready → reserved → moving → returningHome → ready, verificando con assert finali che hold.currentLoad e slot.occupantPid sono coerenti. Un Test Plan piu' ricco aggiunge: una richiesta rifiutata per overweight, una per hold pieno, una sospensione da watchdog.
P4 — Persistenza fuori spec.
La spec non menziona persistenza. Per la demo basta lo stato in-memory, ma e' opportuno dichiararlo esplicitamente come limite nel doc di progetto.
P5 — Tipo di trasporto per la web-gui.
robotoutgui25 (gia' in uso) visualizza una griglia generica di celle colorate. Per la vista a slot etichettati con PID/peso conviene (a) estendere il client esistente con un overlay informativo, oppure (b) realizzare un nuovo cargogui dedicato. La scelta dipende dal tempo disponibile prima della demo.
