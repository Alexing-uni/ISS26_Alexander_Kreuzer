TemaFinale25 – Analisi dei Requisiti

Requirements

Una compagnia di trasporto marittimo (company) intende automatizzare il carico di prodotti nella stiva (hold) di una nave, impiegando un Differential Drive Robot (cargorobot).

I prodotti vanno posti in container di dimensioni predefinite e registrati — specificando il peso — in un database tramite un servizio dedicato (productservice), che restituisce un identificatore univoco PID (numero naturale, PID > 0).

La stiva e' un'area rettangolare piatta con una porta di input/output (IOPort) e 4 slot per i container; l'area slot5 e' permanentemente occupata, gli altri slot sono inizialmente vuoti. Di fronte all'IOPort un sonar rileva la presenza di un container quando misura una distanza D < DFREE/2 per un tempo ragionevole (es. 3 secondi).

La compagnia chiede di costruire un sistema software (cargoservice) che:

  1. riceva la richiesta di caricare nella stiva un container con prodotto gia' registrato nel productservice. La richiesta e' rifiutata se:
    • il peso del prodotto e' troppo alto rispetto al carico massimo della nave MaxLoad > 0 kg;
    • la stiva e' gia' piena (4 slot occupati).
    Se accettata, il cargoservice associa uno slot al PID e ne restituisce il nome; attende quindi che il container venga consegnato all'IOPort. Nel frattempo, le altre richieste non vengono elaborate.
  2. rilevi (tramite il sonar) la presenza del container all'IOPort;
  3. garantisca che il container sia depositato dal cargorobot nello slot riservato. Al termine il cargorobot torna a HOME e il cargoservice puo' elaborare un'altra richiesta;
  4. mostri lo stato corrente della stiva in una web-gui aggiornata dinamicamente;
  5. interrompa ogni attivita' e accenda un LED se il sonar misura D > DFREE per almeno 3 secondi (sospetto guasto sonar). Le attivita' riprendono non appena D ≤ DFREE.

Analisi dei requisiti

Goal: formalizzare le entita' del dominio escludendo le ambiguita' del linguaggio naturale ed esprimendole in un linguaggio comprensibile a un computer (dichiarazioni Java per il dominio + modello qak per le interazioni).

Entita' formalizzate

Product — oggetto registrato nel productservice, identificato da PID e peso:

public class Product {
    int    pid;     // > 0, assegnato da productservice
    double weight;  // kg
}

ProductService — servizio esterno che fa da database dei prodotti:

public interface IProductService {
    int     register( double weight );  // restituisce PID univoco
    Product lookup( int pid );          // restituisce Product o null
}

Slot — area di stoccaggio nominata della stiva:

public class Slot {
    String  name;          // "slot1" .. "slot4", "slot5"
    int     posX, posY;    // posizione nella mappa (celle DR x DR)
    boolean occupied;
    Integer occupantPid;   // null se libero
    boolean permanent;     // true solo per slot5
}

Hold — aggregato dei 4 slot caricabili + slot5 permanente, con vincolo MaxLoad:

public class Hold {
    Slot[]  slots;         // 5 elementi: 4 caricabili + slot5 permanente
    double  maxLoad;       // kg, costante
    double  currentLoad;   // somma dei pesi dei container presenti
    String  reserve( Product p );    // restituisce slotName o null se non possibile
    void    confirmPlaced( String slotName, int pid );
    void    free( String slotName );
}

CargoRobot e DDR del committente — il committente mette a disposizione un Differential Drive Robot (DDR). Nel dominio del problema lo chiamiamo cargorobot: e' lo stesso robot fisico, denominato in base al suo ruolo (trasportare container). Non e' parte del software da costruire: e' una risorsa data.

public interface IRobotBasicMoves {
    void forward( int time ) throws Exception;
    void backward(int time ) throws Exception;
    void left(    int time ) throws Exception;
    void right(   int time ) throws Exception;
    void halt()              throws Exception;
}

A livello di requisiti il cargorobot espone solo le mosse base. Resta da chiarire (vedi D1) se il committente fornisce anche la capacita' di raggiungere una posizione-obiettivo, o se tale pianificazione e' parte del software da realizzare.

Sonar (IOPort) — sensore fisso di fronte all'IOPort che misura la distanza D di un eventuale oggetto. Dai suoi valori il sistema deve riconoscere due condizioni, entrambe fissate dal committente:

container presente : D < DFREE/2  per un tempo ragionevole (es. 3 s)
sospetto guasto    : D > DFREE    per almeno 3 s

LED — attuatore che il sistema accende in caso di sospetto guasto del sonar.

WebGui — vista dinamica dello stato corrente della stiva (slot occupati/liberi).

Struttura: componenti logici

  • il cargoservice (il software da costruire);
  • il productservice (servizio esterno, dato dal committente);
  • il cargorobot (il DDR fornito dal committente);
  • il sensore IOPort (sonar) e l'attuatore LED.

Trattandosi di componenti logicamente (micro)servizi a scambio di messaggi, formalizziamo la struttura con il linguaggio qak.


Un modello dei requisiti

Il cargoservice e' il componente centrale: proattivo (gestisce la richiesta di carico e comanda il cargorobot) e reattivo (alla presenza del container all'IOPort e al sospetto guasto del sonar). Lo modelliamo come QActor; il sonar e il robot sono entita' esterne con cui interagisce a scambio di messaggi.

Core Business e Goal dello Sprint1

Domanda al committente: e' corretto concordare che il 'core business' del
cargoservice consiste anzitutto nel portare un container nello slot riservato
muovendo il cargorobot, mentre la rilevazione col sonar, il watchdog/LED e la
web-gui sono aspetti secondari, da affrontare in sprint successivi?
Goal dello Sprint1. Realizzare il cargoservice che, ricevuta una loadrequest(PID) valida, verifica i vincoli (peso, slot disponibile), riserva uno slot e comanda il cargorobot a portare il container fino allo slot riservato; al termine il robot torna a HOME e il servizio e' pronto per una nuova richiesta.

Per lo Sprint1 si assume il container gia' presente all'IOPort (si ignora la rilevazione tramite sonar) e si ignorano il watchdog/LED (requisito 5) e la web-gui (requisito 4), lasciati a evoluzioni successive.

Domande aperte al committente

D1. Cargorobot e DDR: il committente fornisce il DDR con le sole mosse base,
    oppure fornisce anche la capacita' di raggiungere una posizione-obiettivo (X,Y)?
    Nel secondo caso, la pianificazione del percorso e' parte del software da realizzare?

D2. Posizione di slot5: il quinto slot e' una posizione fissa e nota a priori,
    oppure il cargoservice la scopre dalla mappa all'avvio?

D3. Vincolo MaxLoad: "product-weight evaluated too high" significa
    (a) currentLoad + weight > MaxLoad (vincolo cumulativo) oppure
    (b) weight > MaxLoad (vincolo per-container)?

D4. Hold pieno: se i 4 slot sono occupati, la richiesta e' rifiutata
    definitivamente o accodata? (la spec non prevede operazioni di scarico)

D5. Dimensione dei container: "predefined dimensions" significa che ogni
    container occupa esattamente una cella della stiva, oppure piu' celle?

D6. Posizione dell'IOPort: e' fissa e nota, oppure e' un parametro della mappa?

D7. Comportamento durante il sospetto guasto: una richiesta in arrivo mentre
    le attivita' sono sospese va rifiutata, accodata, o il canale e' chiuso?

D8. Stato iniziale e persistenza: dopo un riavvio si recupera lo stato della
    stiva, oppure si riparte sempre da "4 slot vuoti + slot5 occupato"?

D9. Deposito del container: il cargorobot preleva e deposita fisicamente il
    container (servirebbe un attuatore di presa), oppure il deposito si modella in
    modo astratto (il robot raggiunge IOPort e slot, il trasferimento e' implicito)?

D10. Concorrenza: la spec dice "in the meantime, other requests are not
    elaborated". Le richieste concorrenti sono rifiutate o accodate?

Problematiche aperte (per l'analista)

P1 — Ruolo del cargorobot nel trasferimento del container.
Il DDR fornito dal committente sa muoversi, ma la spec richiede che il container sia depositato nello slot. Occorre stabilire se il trasferimento e' una capacita' del robot (presa/rilascio) oppure va modellato in modo astratto (il robot raggiunge IOPort e slot, il trasferimento e' implicito). E' la stessa questione sollevata in D1 e D9.
P2 — Come modellare il sensore IOPort.
E' sufficiente porre del software sul dispositivo che ospita il sonar, oppure conviene un componente dedicato che intermedia tra il sonar e il cargoservice, riconoscendo le condizioni di "container presente" e "sospetto guasto"? (analoga alla scelta fatta per il radar nel progetto DDRBoundary)
P3 — Granularita' del Test Plan automatizzato (richiesto dalla valutazione).
Il caso minimo significativo e' una richiesta di carico completa, dall'accettazione fino al ritorno del robot a HOME, verificando alla fine che lo stato della stiva sia coerente (slot occupato dal PID atteso, carico aggiornato). Un Test Plan piu' ricco aggiunge i casi di rifiuto (peso eccessivo, stiva piena) e la sospensione per sospetto guasto del sonar.
P4 — Persistenza fuori spec.
La spec non menziona persistenza. Per la demo basta lo stato in-memory, ma e' opportuno dichiararlo esplicitamente come limite nel doc di progetto.
P5 — Tipo di trasporto per la web-gui.
robotoutgui25 (gia' in uso) visualizza una griglia generica di celle colorate. Per la vista a slot etichettati con PID/peso conviene (a) estendere il client esistente con un overlay informativo, oppure (b) realizzare un nuovo cargogui dedicato. La scelta dipende dal tempo disponibile prima della demo.
