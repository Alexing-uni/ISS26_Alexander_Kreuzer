TemaFinale25 – Analisi del Problema (Sprint1)

Scopo

Questo documento sviluppa l'analisi del problema limitatamente allo Sprint1, il cui core business e' stato concordato con il committente: portare un container nello slot riservato muovendo il cargorobot. Si parte dai requisiti gia' formalizzati (TemaFinale25 – Analisi dei Requisiti) e se ne costruisce un modello logico (attori, messaggi, comportamento), senza ancora scegliere i dettagli realizzativi (fase di progetto).

Lo Sprint1 copre i punti 1 e 3 della specifica. In particolare: "If the request is accepted, the cargoservice associates a slot to the product PID and returns the name of the reserved slot" e "is able to ensure that the product container is placed by the cargorobot within its reserved slot. At the end of the work: the cargorobot should return to its HOME location; the cargoservice can process another load-request".

Si assume il container gia' presente all'IOPort (punto 2 escluso); sono esclusi anche la web-gui (punto 4) e il watchdog/LED (punto 5).

Architettura logica

Lo Sprint1 coinvolge tre componenti logici a scambio di messaggi:

Attore Tipo Responsabilita' nello Sprint1
cargoservice da costruire riceve la richiesta, verifica i vincoli, riserva lo slot, coordina il cargorobot
productservice esterno (dato) dato un PID, fornisce il peso del prodotto
cargorobot esterno (DDR del committente) raggiunge una posizione-obiettivo su comando

Il cargoservice incapsula lo stato del dominio (la stiva), gia' formalizzato in fase di requisiti: 

Hold:  4 slot caricabili (+ slot5 permanente), maxLoad, currentLoad
Slot:  name, posizione (X,Y), occupied, occupantPid

Modello delle interazioni

Si individuano i messaggi necessari allo Sprint1 (notazione qak):

//---- committente -> cargoservice
Request  loadrequest    : loadrequest(PID)
Reply    loadaccepted   : loadaccepted(SLOT)        for loadrequest
Reply    loadrejected   : loadrejected(REASON)      for loadrequest
            REASON = overweight | holdfull | unknownpid

//---- cargoservice -> productservice
Request  productweight  : productweight(PID)
Reply    weightis       : weightis(PID, W)          for productweight
Reply    nosuchpid      : nosuchpid(PID)            for productweight

//---- cargoservice -> cargorobot  (contratto moverobot, come in robotsmart26)
Request  moverobot      : moverobot(TARGETX, TARGETY, STEPTIME)
Reply    moverobotdone  : moverobotok(ARG)                     for moverobot
Reply    moverobotfailed: moverobotfailed(PLANDONE, PLANTODO)  for moverobot

Comportamento del cargoservice (modello qak)

Il comportamento del cargoservice e' espresso direttamente in qak (QActor):

QActor cargoservice context ctxcargo
        withobj hold using "domain.Hold(...)" {     //Hold incapsula slot, MaxLoad, mappa
  [# var Pid      = ""
     var Slot     = ""
     var W        = 0.0
     val StepTime = 400
  #]
  State s0 initial {
     println("$name | starts") color blue
  }
  Goto ready

  State ready {                                      //unico stato che accetta richieste
     println("$name | ready, attende loadrequest") color yellow
  }
  Transition t0
     whenRequest loadrequest -> askWeight

  State askWeight {
     onMsg( loadrequest : loadrequest(PID) ){
        [# Pid = payloadArg(0) #]
        request productservice -m productweight : productweight($Pid)
     }
  }
  Transition t0
     whenReply weightis  -> evalRequest
     whenReply nosuchpid -> rejectUnknown

  State evalRequest {
     onMsg( weightis : weightis(PID,WVAL) ){
        [# W = payloadArg(1).toDouble(); Slot = "" #]
        //la forma del vincolo MaxLoad (cumulativo o per-container) e' la D3
        if [# hold.isFull() #] {
           replyTo loadrequest with loadrejected : loadrejected(holdfull)
        }
        if [# !hold.isFull() && !hold.fits(W) #] {
           replyTo loadrequest with loadrejected : loadrejected(overweight)
        }
        if [# !hold.isFull() && hold.fits(W) #] {
           [# Slot = hold.reserve(Pid, W) #]
           replyTo loadrequest with loadaccepted : loadaccepted($Slot)
        }
     }
  }
  Goto carrying if [# Slot != "" #] else ready

  State rejectUnknown {
     replyTo loadrequest with loadrejected : loadrejected(unknownpid)
  }
  Goto ready

  State carrying {                                   //Sprint1: container assunto all'IOPort
     [# val IOX = hold.ioportX(); val IOY = hold.ioportY() #]
     request cargorobot -m moverobot : moverobot($IOX, $IOY, $StepTime)
  }
  Transition t0
     whenReply moverobotdone   -> carryToSlot
     whenReply moverobotfailed -> abort

  State carryToSlot {
     [# val SX = hold.slotX(Slot); val SY = hold.slotY(Slot) #]
     request cargorobot -m moverobot : moverobot($SX, $SY, $StepTime)
  }
  Transition t0
     whenReply moverobotdone   -> goHome
     whenReply moverobotfailed -> abort

  State goHome {
     [# hold.confirmPlaced(Slot, Pid) #]             //container depositato nello slot
     request cargorobot -m moverobot : moverobot(0, 0, $StepTime)   //HOME
  }
  Transition t0
     whenReply moverobotdone   -> ready
     whenReply moverobotfailed -> abort

  State abort {
     println("$name | move fallito: libero lo slot") color red
     [# hold.free(Slot) #]
  }
  Goto ready
}
Il requisito 1 "In the meantime, other requests are not elaborated" e' reso dal fatto che solo lo stato ready ha la transizione whenRequest loadrequest: negli altri stati il cargoservice non raccoglie nuove richieste. Se trattarle con rifiuto o con accodamento e' la domanda aperta D10.

Decisioni sulle problematiche

P1 — trasferimento del container. Il DDR del committente non dispone di un attuatore di presa. Per lo Sprint1 il placement e' modellato in modo astratto: il container si considera depositato nello slot quando il cargorobot raggiunge la posizione dello slot partendo dall'IOPort. Coerente con il requisito "placed by the cargorobot within its reserved slot" senza richiedere hardware aggiuntivo.
Raggiungimento di una posizione. Il cargoservice usa il solo messaggio astratto moverobot(X,Y). Se tale capacita' sia nativa del DDR o realizzata da uno strato di pianificazione e' la domanda D1: nel modello dello Sprint1 e' irrilevante, poiche' il cargoservice dipende solo dal contratto moverobot / moverobotdone.

Piano di test dello Sprint1

Come nel DDRBoundary, il cargoservice mantiene una rappresentazione dello stato della stiva che evolve in conseguenza delle azioni comandate. Il test e' automatizzabile confrontando lo stato finale con quello atteso.

  1. Carico nominale (PASS): stiva con slot2 libero, loadrequest(7) con peso compatibile. Al termine si verifica che: 
    slot2.occupied == true  &&  slot2.occupantPid == 7
hold.currentLoad == currentLoad_iniziale + 120
posizione robot == HOME
stato cargoservice == ready
  2. Rifiuto per peso (PASS se rifiutato): loadrequest con peso che supera il limite MaxLoad → attesa loadrejected(overweight) e stiva invariata.
  3. Rifiuto per stiva piena (PASS se rifiutato): 4 slot occupati → attesa loadrejected(holdfull) e stiva invariata.
  4. PID sconosciuto (PASS se rifiutato): loadrequest con PID non registrato → attesa loadrejected(unknownpid).

Il caso 1 e' il Test Plan significativo richiesto per la demo: copre l'intero ciclo ready → checking → carrying → returning → ready ed e' verificabile con assert finali (PASS/FAIL) integrabili in JUnit o nel log di collaudo.
