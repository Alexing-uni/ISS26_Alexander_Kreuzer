Progetto robotservice26 – Il robot come microservizio

Introduction

Robot-as-a-Service – Capitolo 27 del Protobook
Goal: Esporre il Differential Drive Robot (VirtualRobot26) come un microservizio raggiungibile via rete e osservabile via eventi. Il componente robotservice26 incapsula il POJO RobotObj26 dentro un QActor (robotactor) e definisce esplicitamente i messaggi-comando (Dispatch e Request) che un'applicazione puo' inviare al robot.

Il progetto e' il riferimento operativo della lezione del 20/05 ed e' la risposta alla problematica P1 sollevata nell'analisi del DDRBoundary: "conviene usare RobotObj26 (POJO) o RobotService26 (servizio a messaggi)?". Questo progetto realizza la seconda alternativa, collocando il sistema nell'alveo dei Sistemi a Microservizi.

Requirements

R1  Esporre il VirtualRobot26 come servizio raggiungibile via rete,
    in modo che client diversi possano comandarlo senza conoscere
    i dettagli del trasporto WebSocket.

R2  Definire esplicitamente i messaggi-comando del robot:
       - move(M)      : mosse sincrone (l|r|a|d|h)
       - cmd(MOVE,T)  : mosse asincrone (w|s) con reply
       - step(TIME)   : mossa atomica di durata TIME

R3  Rendere il robot OSSERVABILE: emettere eventi (vrinfo, sonardata,
    sonaralarm) che i client di sistema possono sottoscrivere.

R4  Disaccoppiare la logica applicativa (boundaryworker) dalla
    tecnologia del robot tramite messaggi qak tipati.

Requirement analysis

L'uso di RobotService26 rispetto all'uso diretto di RobotObj26:

  • rende esplicite le interazioni logiche tra applicazione e robot (ogni comando e' un messaggio dichiarato nel modello qak);
  • puo' introdurre ritardi di rete, che pero' si annullano se il servizio gira sullo stesso nodo dell'applicazione;
  • colloca il sistema nell'architettura a microservizi, dove ogni componente e' un servizio autonomo a scambio di messaggi.

Il robotactor e' al tempo stesso:

  • server di comandi: riceve move/cmd/step ed agisce sul robot;
  • produttore di eventi: si iscrive a se stesso (subscribeTo robotactor for sonardata) e ridistribuisce gli eventi del robot ai client di sistema.

Problem analysis

Il modello qak distingue tre semantiche di comando:

Messaggio Tipo Semantica
move(M) Dispatch Mossa sincrona fire-and-forget (l=left, r=right, a=avanti, d=dietro, h=halt)
cmd(MOVE,T) Request/Reply Mossa asincrona (w=walk, s=stop) con conferma cmddone o cmdfailed
step(TIME) Request/Reply Mossa atomica di durata TIME ms con reply stepdone/stepfailed

Gli eventi prodotti dal servizio:

Evento Origine Uso
vrinfo(SOURCE,INFO) VirtualRobot Stream di stato del robot
sonardata(DISTANCE) Sonar Lettura grezza del sonar
sonaralarm(DISTANCE) robotactor Allarme per i client di sistema (es. boundaryworker)

Il POJO RobotObjForQak e' incapsulato nel QActor tramite la clausola withobj robot using "robots.RobotObjForQak(...)": questo e' il pattern QAK per inserire oggetti Java dentro un attore (cap. 22.7 del Protobook). 

QActor robotactor context ctxrobotservice26
        withobj robot using "robots.RobotObjForQak(\"localhost\",myself,\"logs/robotactor.log\")" {
    State s0 initial {
        subscribeTo robotactor for sonardata
        subscribeTo robotactor for vrinfo
    }
    Goto work
    State work { }
    Transition t0
        whenMsg     move -> domove
        whenRequest cmd  -> docmdreq
        whenRequest step -> handleAsynchStep
    ...
}

Test plans

  1. Test del servizio standalone: avviare il VirtualRobot26 (Node), poi robotservice26. Verificare che il servizio si connetta al robot (porta 8091) e si metta in attesa di comandi sulla porta 8125.
  2. Test comando sincrono: inviare move(a) da un client. Verificare che il robot avanzi nella scena 3D.
  3. Test comando asincrono con reply: inviare cmd(w,1000). Verificare la ricezione di cmddone.
  4. Test step atomico: inviare step(345) e verificare stepdone con la durata effettiva.
  5. Test observability: un client si iscrive a vrinfo e sonardata; verificare la ricezione degli eventi in streaming.

Testing

Il servizio si avvia con gradlew run dopo aver acceso il VirtualRobot26. Per il collaudo dei comandi si puo' usare un client qak (es. il boundaryworker che dichiara ExternalQActor robotactor context ctxrobotservice26) oppure un client WebSocket/HTTP diretto.

Il vantaggio rispetto a RobotObj26 e' che il contratto di interazione (i messaggi) e' esplicito e verificabile: si puo' testare ogni comando in isolamento e osservare la sequenza di eventi prodotta.


Maintenance

robotservice26 e' il livello di accesso al robot per il TemaFinale25: il cargoservice comandera' il cargorobot inviando esattamente questi messaggi (move, cmd, step) e osservando gli eventi (vrinfo, sonardata).

  • Estensione comandi: aggiungere pickup e place come nuove Request per il caricamento dei container del TemaFinale.
  • Deployment distribuito: grazie al Dockerfile, il servizio puo' girare su un nodo separato; basta cambiare l'host nel Context dei client.
  • Integrazione sonar reale: sostituire la sorgente di sonardata con il PicoW fisico (o il mock mockPicowRadar.py) senza modificare i client che consumano gli eventi.
