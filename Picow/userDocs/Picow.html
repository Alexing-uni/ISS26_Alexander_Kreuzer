Progetto Picow – Raspberry Pi PICOW: sonar HC-SR04 e firefly hardware

Introduction

SISTEMA SPERIMENTALE DI N LUCCIOLE
Goal: Portare il modello QAK fuori dalla simulazione e in hardware reale usando il microcontrollore Raspberry Pi Pico W (PICOW). Tre famiglie di esempi:
  • controllo di un sensore sonar HC-SR04 per la rilevazione di ostacoli;
  • controllo di LED come firefly hardware (sostituzione del rendering simulato con luce fisica);
  • comunicazione WiFi tramite TCP e MQTT verso il sistema QAK su PC.

Il progetto e' il riferimento operativo della lezione del 14/05 (settimana 14) e materializza la chiusura del cerchio: dal modello formale QAK al firmware MicroPython sul microcontrollore.

Requirements

R1  Utilizzare il Raspberry PICOW per attivare il sonar HC-SR04 e
    ottenere misure di distanza in cm in modo continuativo.

R2  Pubblicare le misure su un broker MQTT cosi' che il sistema QAK
    su PC le possa consumare come Event.

R3  Pilotare uno o piu' LED con pattern di flash che simulino il
    comportamento di una lucciola, attivati da messaggi MQTT in arrivo
    dal sistema QAK firefly.

R4  Fornire un esempio di sistema sperimentale di N lucciole hardware
    in cui ogni PICOW e' una lucciola e il pattern di sincronizzazione
    e' lo stesso del modello fireflySynchCoreog.qaktt (coreografato).

Requirement analysis

Il PICOW (RP2040 dual-core + WiFi/BLE) e' la naturale piattaforma di embedded per progetti didattici: economico, programmabile in MicroPython, dotato di WiFi nativo, supporta GPIO con tempi di risposta deterministici per il sonar HC-SR04.

L'analisi distingue tre componenti software sul PICOW:

  • Acquisizione sensori (sonar0.py, dht22.py): codice GPIO bare-metal per il sonar (Trig/Echo pin) e per sensori ambientali (DHT22).
  • Comunicazione (wifi.py, tcp_client.py, claudeMqtt.py): astrazione del WiFi e dei client TCP/MQTT. Il file secrets.py contiene le credenziali WiFi.
  • Applicazioni composite (sonarMqtt.py, sonarWeb.py, firefly00Mqtt.py): combinano sensore + comunicazione in scenari completi.

Problem analysis

Il primo problema progettuale e' la connettivita' WiFi: il PICOW deve resettare e re-tentare la connessione in caso di fallimento. Il pattern adottato e': 

import wifi
wifi.connect()        # blocca fino a connessione, retry interno
# da qui in poi, socket TCP/MQTT funzionano

Il secondo problema e' la scelta del protocollo di trasporto:

Protocollo Pro Contro File esempio
TCP raw Latenza minima, full duplex Senza broker: PC e PICOW si devono conoscere a vicenda tcp_client.py, tcpServer.py
MQTT Pub/sub disaccoppiato, riconnessione automatica Latenza extra del broker, dipendenza esterna claudeMqtt.py, sonarMqtt.py, firefly00Mqtt.py
HTTP server Web dashboard direttamente sul PICOW Modello request-response, no push web_server.py, sonarWeb.py, indexSonar.html

Il terzo problema riguarda il controllo temporale del sonar: HC-SR04 richiede un impulso Trig di 10 µs e misura il tempo di andata-ritorno dell'eco. La temporizzazione precisa (microsecondi) e' delegata alle primitive GPIO di MicroPython.


Test plans

Il piano di collaudo segue una scala di complessita' crescente:

  1. Test base GPIO: caricare ledOnOff.py sul PICOW; il LED on-board deve lampeggiare.
  2. Test sonar standalone: caricare sonar0.py; il REPL deve stampare misure di distanza in cm.
  3. Test WiFi: configurare secrets.py con le credenziali, caricare wifi.py, verificare che il PICOW ottenga IP DHCP.
  4. Test integrato sonar + MQTT: avviare un broker MQTT (mosquitto), caricare sonarMqtt.py; il PC deve poter sottoscrivere al topic e ricevere le misure.
  5. Test firefly hardware: caricare firefly00Mqtt.py; il sistema QAK fireflySynchCoreog su PC deve poter sincronizzare i lampeggi del LED PICOW emettendo eventi MQTT.

Project

Il progetto e' una raccolta di script MicroPython da caricare sul PICOW. La struttura del filesystem PICOW dopo il deployment e' piatta (tutti i .py in /).

Boot e firmware

  • RPI_PICO2_W-20260406-v1.28.0.uf2 — firmware MicroPython aggiornato (drag-and-drop in modalita' BOOTSEL).

Configurazione e librerie

  • secrets.py — credenziali WiFi (NON committare in repo pubblici se si modificano).
  • wifi.py — connessione WiFi con retry automatico.
  • simple.py — client MQTT minimalista (porting di umqtt.simple).

Esempi sonar

  • sonar0.py — lettura HC-SR04 base.
  • sonarMqtt.py — sonar che pubblica su MQTT.
  • sonarWeb.py + indexSonar.html — dashboard web del sonar.

Esempi firefly

  • ledFF1.py — pattern di flash su LED (singolo PICOW).
  • firefly00Mqtt.py — lucciola PICOW che ascolta eventi flash via MQTT.

Esempi rete

  • tcpConn.py, tcpServer.py, tcp_client.py, tcp_client_async.py — varianti TCP.
  • claudeMqtt.py — wrapper MQTT didattico.
  • web_server.py, index.html — mini HTTP server.

Sensori aggiuntivi

  • dht22.py — sensore di temperatura/umidita' DHT22.
  • testFileRead.py — test del filesystem flash del PICOW.

Testing

Il testing avviene direttamente sul dispositivo tramite REPL MicroPython (Thonny IDE consigliato): 

1. Collegare il PICOW al PC via USB
2. Aprire Thonny e selezionare l'interprete "MicroPython (Raspberry Pi Pico)"
3. Caricare i file .py necessari nel filesystem PICOW
4. Eseguire dal REPL: import sonar0
5. Osservare i print di debug sulla console di Thonny

Per il test di integrazione con il sistema QAK su PC:

  1. Avviare il broker mosquitto in locale o usare uno cloud (HiveMQ).
  2. Modificare BROKER in sonarMqtt.py con l'IP del broker.
  3. Sul PC, lanciare fireflySynchCoreog dal progetto firefly dopo aver modificato il broker MQTT nel contesto QAK.
  4. Verificare la sincronizzazione dei lampeggi LED hardware con il modello simulato.

Maintenance

Il progetto e' progettato per essere esteso facilmente verso scenari piu' complessi:

  • Sistema sperimentale N-lucciole hardware (chap. 23.7 del Protobook): replicare il setup di firefly00Mqtt.py su N PICOW, ciascuno con LED proprio. Il modello QAK fireflySynchCoreog orchestrera' la sincronizzazione globale via MQTT.
  • Sonar nel Boundary Walk: integrare sonarMqtt.py come Radar virtuale nel progetto vrUsage26. Il VirtualRobot26 leggera' la distanza reale del sonar per la logica anti-intruso.
  • OTA update: aggiungere un meccanismo di aggiornamento via WiFi degli script MicroPython, evitando la necessita' di scollegare-ricollegare il PICOW.

Il PICOW costituisce il nodo edge di un'architettura piu' ampia che vede al centro il sistema QAK come orchestratore/coreografo. La separazione netta fra firmware (MicroPython, GPIO, MQTT publisher) e modello (QAK, FSM, business logic) e' un caso esemplare di Clean Architecture applicata a sistemi cyber-fisici.
