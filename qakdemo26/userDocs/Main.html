Laboratorio 2 – Analisi Comparativa: SistemaSJavalin vs Modello ad Attori QAK

Introduction

ISS26 – Ingegneria dei Sistemi Software
Obiettivo Lab 2: Analizzare criticamente due approcci architetturali per la descrizione di sistemi software: il sistema imperativo basato su Javalin (SistemaSJavalin / SistemaSJavalinBetter) e il modello dichiarativo ad attori QAK. Inoltre, modellare il comportamento di un sistema di lucciole sincronizzate mediante QAK (1, 3 e 100 lucciole).

Il laboratorio approfondisce il confronto tra programmazione orientata agli oggetti con thread e il paradigma ad attori con messaggi tipati, evidenziando vantaggi, limiti e scenari di applicazione di ciascun approccio.

Requirements

Le attività richieste sono:

   - SistemaSJavalin / SistemaSJavalinBetter (approccio imperativo con Javalin)
   - Modello dichiarativo ad attori QAK (QActors come FSM di Moore)

 Task 2: Definire un modello QAK che simuli il comportamento di UNA lucciola.
   - La lucciola si carica per un periodo fisso (1000 ms) ed emette un flash.
   - Il ciclo si ripete indefinitamente.

 Task 3: Estendere il modello per simulare TRE lucciole sincronizzate.

   - Meccanismo integrate-and-fire: quando una lucciola percepisce il flash
     di un'altra, avanza la propria fase e lampeggia immediatamente.

   - Il sistema dimostra sincronizzazione emergente a scala.

Requirement Analysis

La domanda centrale del laboratorio è: cosa guadagna e cosa perde lo sviluppatore passando da un sistema OO con thread a un sistema ad attori con messaggi tipati?

SistemaSJavalin rappresenta l'approccio tradizionale: un server Javalin configurato in modo imperativo, dove route HTTP e handler WebSocket sono registrati direttamente come lambda. Il sistema è semplice da avviare ma accoppia fortemente il trasporto con la logica di dominio.

Il modello QAK (QActors) è un DSL esterno costruito su Xtext che descrive il sistema in modo dichiarativo. Ogni QActor è una Macchina a Stati di Moore (FSM) con stati, transizioni tipate e una coda di messaggi privata. Il sistema di lucciole è il caso d'uso scelto per dimostrare la scalabilità del modello.

  • 1 lucciola: verifica il ciclo base carica-flash senza sincronizzazione.
  • 3 lucciole: introduce il meccanismo integrate-and-fire e il periodo refrattario.
  • 100 lucciole: dimostra la scalabilità mediante attori dinamici (coroutine Kotlin) e sincronizzazione emergente.

Problem Analysis

Il confronto tra i due approcci evidenzia differenze fondamentali su più dimensioni:

Configurazione e architettura:
SistemaSJavalin configura il sistema passo dopo passo nel codice: la topologia è implicita nel flusso di esecuzione. Il modello QAK la rende esplicita nel DSL (contesti, attori, messaggi), separando nettamente il "cosa" dal "come".

Concorrenza:
Javalin gestisce un pool di thread del SO: operazioni bloccanti in un handler paralizzano quel thread. I QActors sono coroutine Kotlin: leggere, non bloccanti e prive di stato condiviso. 100 lucciole come 100 thread del SO sarebbero costose; come 100 coroutine sono banali.

Messaggi:
In Javalin i messaggi sono stringhe o JSON grezzi senza contratto formale. In QAK, Dispatch, Request/Reply ed Event sono tipi di prima classe validati dal compilatore.

Distribuzione:
SistemaSJavalin risiede in una sola JVM; scalarlo richiede infrastruttura esterna. In QAK, spostare un attore su un altro nodo richiede solo di cambiare host nel contesto. Il trasporto (TCP o MQTT) è intercambiabile senza modificare la logica dell'attore.

Sincronizzazione emergente (lucciole):
Il modello integrate-and-fire è implementato con tre primitive QAK: whenEvent flash (percezione), Goto doFlash if shouldSync (avanzamento di fase) e discardMsg On + delay 200 (periodo refrattario). A 100 attori, la sincronizzazione globale emerge dalle sole regole locali, senza coordinatore centrale. 

// Esempio: ciclo base di una lucciola in QAK
State charging { }
Transition t0
    whenTime 1000   -> doFlash
    whenEvent flash -> perceiveFlash

State perceiveFlash {
    onMsg( flash : flash(ID) ){ [# shouldSync = payloadArg(0) != name #] }
}
Goto doFlash if [# shouldSync #] else charging

State doFlash {
    emit flash : flash(firefly1)
    discardMsg On
}
Goto refractory

State refractory { delay 200  discardMsg Off }
Goto charging

Test Plans

Il collaudo dei modelli QAK avviene mediante osservazione del log di esecuzione e verifica del comportamento atteso:

  1. Task 2 (1 lucciola): Avviare il sistema firefly1system. Verificare che il log mostri alternanza regolare di messaggi "cargando" e "FLASH!" con intervallo di ~1000 ms.
  2. Task 3 (3 lucciole): Avviare firefly3system. Inizialmente i flash sono sfasati (0/300/600 ms). Criterio di accettazione: dopo poche iterazioni, i tre flash convergono allo stesso istante (sincronizzazione visibile nel log).
  3. Task 4 (100 lucciole): Avviare firefly100system. Verificare che il gestore crei 100 istanze e che gradualmente i flash si sincronizzino. Monitorare l'assenza di deadlock o stack overflow (prova di scalabilità delle coroutine).

Project

I modelli QAK sono definiti in tre file nella directory qakdemo26/src/:

  • firefly1.qak – Sistema firefly1system, porta 8020.
    Un solo QActor firefly1 con variabile FlashPeriod = 1000L e transizione whenTimeVar FlashPeriod. Nessuna sincronizzazione necessaria.
  • firefly3.qak – Sistema firefly3system, porta 8021.
    Tre QActors (firefly1, firefly2, firefly3) con fasi iniziali 0/300/600 ms. Sincronizzazione integrate-and-fire tramite evento flash. Periodo refrattario di 200 ms con discardMsg On/Off.
  • firefly100.qak – Sistema firefly100system, porta 8022.
    QActor fireflymanager crea 100 istanze dinamiche di firefly (marcato dynamicOnly) tramite loop createActorFsmDynamic("firefly", "_$i", false). Ogni istanza sceglie una fase iniziale casuale (0–900 ms). Dimostra il principio "More is Different": sincronizzazione globale emergente da regole locali semplici.

Il documento di analisi comparativa è disponibile in userDocs/ (questo file).


Testing

I modelli QAK non richiedono test unitari tradizionali in quanto il DSL garantisce la correttezza strutturale (stati, transizioni, messaggi tipati) già in fase di compilazione. Il testing funzionale è condotto mediante esecuzione diretta in Eclipse con il plugin QActork, osservando il log colorato prodotto dalle istruzioni println(...) color yellow/cyan/green/blue.

La comparazione con SistemaSJavalin evidenzia che il modello QAK ha una testabilità intrinsecamente migliore: ogni attore è isolato, i messaggi sono formali e la FSM è verificabile per ispezione visiva.


Maintenance

Il confronto finale tra i due approcci:

  • SistemaSJavalin / Better è adatto a servizi piccoli e monolitici dove la semplicità di setup è prioritaria. Diventa debito tecnico in sistemi distribuiti complessi.
  • Modello QAK introduce una curva di apprendimento più alta (DSL + FSM + Prolog) ma produce sistemi più robusti, scalabili e distribuibili. Rimane la scelta naturale per sistemi reattivi, IoT e microservizi.

SistemaSJavalin continua ad avere un ruolo valido come inbound adapter all'interno di un sistema QAK: riceve la richiesta HTTP/WS e la trasforma in un messaggio QAK elaborato dall'attore corrispondente. I due approcci non si escludono; si complementano.
